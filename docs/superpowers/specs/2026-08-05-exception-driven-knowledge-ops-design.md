# PSEAgent 异常驱动知识运营台设计

日期：2026-08-05  
状态：已确认，开始实施  
对应基线：`2026-08-05-live-answer-review-feedback-ux-design.md`

## 1. 问题与原则

现有管理台直接展示数据库英文枚举，并把自动复查和用户反馈作为两份原始记录列表。少量数据时尚可追踪；当数百名用户并发提问时，运营人员无法逐条阅读，也无法从 `new`、`triaged`、`needs_review` 等技术状态直接判断今天应处理什么。

本阶段把后台从“记录浏览器”改为“异常驱动工作台”：正常回答由系统自动归档，人工只处理异常问题组。数据库和 API 枚举继续使用稳定英文值，界面、筛选、帮助与操作全部使用中文业务语言。

## 2. 中文状态展示

前端使用一个穷尽类型的状态词典统一展示，不把中文写回数据库。主要映射为：

- 反馈类型：`useful` 回答有帮助、`incorrect` 答案错误、`missing` 信息不完整、`review_requested` 请求人工复查、`evidence` 证据或引用有问题、`correction` 用户提供了纠正；
- 反馈状态：`new` 待处理、`triaged` 已分类、`in_review` 处理中、`resolved` 已解决、`rejected` 已关闭；
- 复查执行：`queued` 等待复查、`running` 正在复查、`completed` 复查完成、`errored` 复查异常；
- 复查结论：`pending` 等待结论、`pass` 复查通过、`needs_review` 需要人工复核、`fail` 复查未通过；
- 人工状态：`open` 待处理、`in_review` 处理中、`resolved` 已解决、`dismissed` 无需处理。

颜色只作辅助；每个徽标必须同时包含可读中文。原始英文值只在技术详情、审计和导出中保留。

## 3. 管理人员职责

系统负责逐回答复查、正常记录自动收敛、异常聚类、优先级、重复合并和技术异常重试。后台管理员统一负责异常分流、根因判断、确认知识或答案卡修订、触发验证和发布，不再分派负责人。修订 Agent 只能生成有证据的草稿；单个后台管理员是唯一人工确认人，发布仍必须通过自动回归、审计和可回滚门禁。任何模型结论都不能绕过管理员确认直接改写或发布企业知识。

管理人员的默认入口只回答三个问题：

1. 今天有多少必须处理的事项；
2. 哪类问题影响用户最多或风险最高；
3. 当前应在何时前执行哪个明确动作。

## 4. 行动导向总览

总览顶部展示：严重错误、需要人工复核、用户与模型判断冲突、复查执行异常、即将超时、今日自动通过和自动处理率。原始状态分布下沉为辅助分析，不再作为首屏主信息。

主表为“优先处理的问题组”，按优先级、最后出现时间和影响用户数排序。默认隐藏已通过、已解决和无需处理记录。列表支持中文状态和优先级筛选、服务端分页；不提供负责人字段或分配操作。超过 50 行的前端列表使用虚拟化或分页，不一次渲染全部记录。

## 5. 统一问题中心

新增持久化问题组 `issue_cases` 和问题发生记录 `issue_occurrences`。问题组不保存用户原问、原答或聊天名明文，只保存安全标题、卡片标识、缺陷分类、优先级、状态、SLA 和时间；不保存负责人，原始正文仍只存在反馈或复查加密载荷中。

聚类指纹优先使用：知识域 + 答案卡 ID + 缺陷分类；没有答案卡时使用知识域 + 规范化问题哈希 + 缺陷分类。发生记录关联 request id、来源类型、来源记录 id 和伪匿名用户 id，用于计算次数与受影响人数。

问题优先级：

- `P0`：复查 `fail`、关键逻辑冲突或禁答主张；
- `P1`：`needs_review`、用户选择答案错误、用户与模型结论冲突；
- `P2`：信息不完整、请求人工复查、证据问题、重复出现的低风险缺陷；
- `P3`：持续复查异常和一般表达问题。

同一 request id 的反馈和自动复查进入同一问题组；同类记录只增加发生次数，不制造重复工单。`pass` 且无负面反馈不创建问题组；`useful` 只进入统计。

## 6. 问题生命周期

问题组业务状态为：`open` 待处理、`in_progress` 修订中、`validating` 待验证、`resolved` 已解决、`dismissed` 无需处理。后台管理员从待处理直接开始修订，状态变化记录审计事件。

`fail` 和冲突项自动进入待办，但不会撤回已发送回答、修改答案卡或写回知识库。后台管理员在详情中查看关联反馈、复查缺陷和受影响数量，并通过生成草稿、编辑、验证和发布等真实动作推进问题。问题状态不再由管理员任意选择：生成草稿后进入修订中，提交验证后进入待验证，验证失败自动退回修订中，发布成功后才自动进入已解决。管理员只可手工选择无需处理或重新打开。

## 7. 信息架构

主导航调整为：总览、问题中心、答案卡、回归测试、发布中心、审计记录。原始“自动复查”和“用户反馈”作为问题详情中的证据及审计页面保留，不承担主要分流职责。常规问题修复在问题详情的修订工作台完成，答案卡页面只承担高级浏览和历史审计。

桌面端采用高密度、低装饰、Slate 中性色和蓝色主操作。严重、警告、处理中、成功和中性状态使用语义色并配文字；焦点可见，主要操作点击区域不低于 44px，异步操作提供进行中与错误恢复提示。

## 8. 验收

- 管理台业务页面不出现裸英文枚举；数据库仍保留原英文值；
- 总览首屏展示必须处理的异常和明确中文动作，而非原始状态堆叠；
- `pass` 正常记录默认不进入人工待办；
- `needs_review`、`fail`、负面反馈和执行异常自动形成或合并问题组；
- 相同问题组正确累计发生次数与受影响用户数；
- 问题组不新增问题、回答、聊天名或知识正文的明文列；
- 后台管理员可按中文优先级和状态筛选，并按“待处理 → 修订中 → 待验证 → 已解决”流转；
- 页面和 API 均不提供负责人字段、分派动作或“已分配”状态；
- 所有流转写入审计；
- PostgreSQL 迁移、服务、Worker、后台测试、类型检查、构建和浏览器验收通过。

## 9. 知识修订闭环

知识修订采用三层存储：PostgreSQL 保存运营草稿、编辑内容、验证和发布记录；两套 Git/Obsidian 仓库保存正式知识源；不可变发布快照保存线上问答实际加载的答案卡目录和知识版本。草稿永远不直接影响用户。

修订目标按根因路由：已有证据但回答遗漏、规划、引用或表达有问题时修改答案卡；正式资料确实缺失时创建知识页面草稿；检索问题修改答案卡别名、标签和首选证据路径；逻辑或程序问题只创建系统回归任务，不写入知识库；判断冲突等待管理员裁决。

专业技术、产品、迁移和架构问题写入 `coremail-professional`，售前沟通、客户需求和价值表达写入 `presales-general`。跨域问题分别生成两个仓库的修订，再用问题族绑定，不允许一个文件跨仓混写。

## 10. 修订 Agent

修订 Agent 继续使用 `deepseek_v4_flash`。输入为加密载荷解密后的原问题、原回答、自动复查结果、已校验正式证据和现有答案卡；输出必须通过严格 Schema，包含根因、目标类型、目标知识域、标准问题、客户中立别名、必答项、禁答主张、首选证据路径、候选答案和五类回归问题。

Agent 不得使用外部知识，不得把客户名称或原问题明文固化进通用答案卡，不得生成没有正式证据支持的事实。正式资料不足时只能标记“需要补充知识”，不能伪造完整修订。

## 11. 修订数据模型

新增 `knowledge_repair_drafts`、`repair_validation_runs` 和 `repair_publications`。草稿与问题组一对多但同一时间只有一个活动草稿；草稿内容加密保存，明文不得进入问题列表、作业载荷、日志或审计元数据。验证记录保存用例元数据、结果摘要和加密详情；发布记录保存目标 Git 提交、目录哈希、活动快照和回滚信息。

草稿技术状态为 `generating`、`draft_ready`、`validating`、`validation_failed`、`ready_to_publish`、`publishing`、`published`、`failed`。界面只显示中文业务名称，并把失败原因和恢复动作放在当前步骤附近。

## 12. 修订工作台

问题详情升级为可深链的完整工作台，不在窄抽屉中承载主流程。页面顶部显示“确认问题 → 编辑修订 → 自动验证 → 发布生效”四步进度；左侧集中展示原问、原答、复查结论、缺陷和正式证据，右侧展示结构化修订表单和修改差异。

每个状态只提供一个主要操作：无草稿时生成修订草稿，草稿就绪时提交自动验证，验证失败时继续修改，验证通过时发布并应用。复杂 JSON、Git 提交和目录哈希只进入审计记录与发布记录，不进入修订主页面。长表单自动保存，异步按钮禁用并展示进度，失败信息包含可执行的恢复路径。

## 13. 隔离验证

验证必须在允许路径的隔离 Git worktree 中渲染候选 Markdown，不能先改动正式仓库。每份草稿至少包含原始问题、同义改写、口语问法、上下文追问和边界负例五类用例；同时校验答案卡 Schema、正式证据路径、精确或问题族命中、必答项、禁答主张、引用和 `deepseek_v4_flash` 复查结论。

单问题验证通过后仍须通过既有全量发布回归。任一关键或主要缺陷、缺失证据、目录漂移或知识版本漂移都会使验证失败并自动把问题退回修订中。

## 14. 发布与生效

管理员点击发布后，Worker 在已验证的基线提交上将允许路径写回目标 Obsidian 仓库，生成可审计 Git 提交，重新编译答案卡目录和知识索引，并创建包含两个知识域版本的不可变快照。只有全部制品成功后才原子切换活动指针。

问答服务改为监听活动快照或按版本热加载答案卡目录，不再依赖人工重启。发布后使用原始问题调用正式问答链路并确认答案卡已激活；成功后自动关闭问题，失败则恢复上一活动快照并保留修订中状态。

## 15. 单管理员门禁

移除“创建人不能审核自己的修订”和“发布发起人不能是唯一批准人”这两项多人分工限制。替代门禁为：Agent 只能起草、管理员显式确认、自动回归必须通过、发布全程审计、活动版本可一键回滚。单个管理员能够完成闭环，但不能跳过验证直接把草稿标记为已解决。

## 16. 新增验收条件

- 管理员无需填写答案卡 JSON、Git SHA 或发布清单；
- 从问题详情最多通过“生成草稿、提交验证、发布应用”三个主要动作完成修复；
- 草稿生成后问题自动进入修订中，发布成功后才自动进入已解决；
- 验证失败展示具体失败用例和恢复动作，并自动退回修订中；
- 发布答案卡能被原始问题和至少两种改写命中，`answerCardActivation.activated` 为真；
- 发布后问答再次经过独立复查且无关键或主要缺陷；
- 任一发布均可恢复上一活动快照；
- 客户名称、原问题、原回答和草稿正文不进入问题列表、日志或审计明文。

## 17. 管理后台账号密码登录

管理后台不再要求管理员复制 Bearer Token。登录页改为账号、密码两项凭据；服务端使用配置中的管理员账号和 scrypt 密码哈希校验，成功后签发高熵、短时、仅保存在服务端内存中的管理会话。浏览器只在当前标签页的 `sessionStorage` 保存会话令牌，不保存账号密码；API 或浏览器关闭会话、服务重启、会话过期后均须重新登录。

管理会话只代表单一 `admin` 角色，不新增负责人或多人分配能力。论客 Bridge、Worker、发布探针等服务间调用继续使用独立 Bearer Token，不能使用管理员账号密码，也不能把管理员会话作为长期服务凭据。

管理员密码明文不得进入 Git、数据库、日志、审计或前端构建产物。仓库只记录配置项名称和哈希生成方法，真实账号及密码哈希由 `.env.local` 或生产秘密管理系统注入。登录失败统一返回“账号或密码错误”，不泄露账号是否存在；登录表单提供可见标签、密码显隐、自动填充、提交中状态和字段附近的可恢复错误提示。

验收条件：

- 未登录访问业务 API 返回 401，正确账号密码可换取管理会话；
- 错误账号或密码均返回同一错误，响应不包含配置哈希或明文；
- 退出登录立即吊销当前会话，会话过期或服务重启后不能继续使用；
- 管理后台不再出现“访问令牌”输入框，密码不会写入浏览器存储；
- 服务角色 Bearer Token 的反馈与自动复查写入链路保持兼容。

## 18. 完整修订草稿与工作台降噪

“生成修订草稿”必须优先用当前活动答案卡目录重新匹配问题，不能只依赖问题产生当时保存的答案卡标识。旧问题在后续答案卡发布后再次生成草稿时，Worker 应使用原问题重新查找当前标准问题和别名；命中后加载答案卡正文、必答项首选证据路径、原问题、原回答和复查缺陷，再调用 `deepseek_v4_flash` 生成完整草稿。

可进入验证的草稿必须同时包含非空标准答案、至少一条同义或口语问法、必答项、正式证据路径和五类回归问题。没有正式证据时，Agent 继续失败关闭，但界面只展示阻塞原因和“重新生成完整草稿”动作，不把空答案、空同义问法或空验证问题伪装为可编辑草稿。知识版本或答案卡目录更新后，管理员可在同一活动草稿上重新生成，系统重新读取最新正式证据并覆盖旧的阻塞结果。

修订工作台只展示管理员完成决策所需的信息。回答变化预览仅在原回答和非空修订答案同时存在时显示，不使用“等待补充”等占位文字。Git 路径、提交、目录哈希、快照 ID 等高级技术字段从修订主页面移除，仍保留在审计记录和发布记录中供排障，不占据日常运营流程。

验收条件：

- 问题产生时未命中答案卡、但当前目录已能由标准问题或别名命中的，生成草稿时应重新关联当前答案卡和正式证据；
- 正常生成完成后，“修订后的标准答案”和“同义问法与口语问法”均非空；
- 不可发布草稿不展示空表单，管理员可直接重新生成；
- 修订工作台不显示高级技术详情，也不出现“等待补充”占位；
- 重新生成过程幂等，生成中的重复点击不产生重复作业。

## 19. 并行修订、批次发布与 GitHub 同步

知识修订改为“并行准备、集中发布”。每个问题仍独立完成生成、人工编辑和自动验证；验证通过的草稿自动进入待发布池，不再从单问题工作台直接写回知识库。管理员可继续打开其他问题进行修订，也可在多个浏览器标签中处理不同草稿，长表单继续自动保存。

后台作业按类型使用受控并发池：自动复查最多并行 4 个、修订草稿生成最多并行 3 个、隔离验证最多并行 2 个；目录同步、Git 写入、批次发布和回滚进入串行维护池。数据库继续使用 `FOR UPDATE SKIP LOCKED` 保证作业只被一个执行槽领取。发布还必须按知识库取得资源锁，因此同一知识库不能并行写入；不同知识库可以同时准备候选制品，但由同一个逻辑发布批次统一决定是否生效。

新增批次记录和批次项目。管理员从待发布池选择一个或多个已验证草稿后创建批次；同一目标文件出现多份草稿时拒绝创建并提示先合并问题证据。同一知识库内的全部候选文件在一个隔离工作树中联合编译和全量回归，通过后合并为一个 Git 提交。一个逻辑批次若同时包含两个知识库，会产生至多两个 Git 提交和两次 push，但在管理台只显示为一个批次。

正式发布顺序为：确认所有草稿验证通过且基线未漂移、联合编译候选目录、运行组合回归、按知识库生成本地提交、以 fast-forward 方式 push 到各自已配置的 GitHub upstream、重新编译正式目录、创建不可变发布快照，最后切换活动版本并关闭关联问题。禁止 force push，未配置 upstream、远端领先、本地脏工作树或 push 失败均不得切换线上版本。

跨两个 GitHub 仓库不存在原生原子 push。系统在全部本地提交成功后才开始远端同步；若部分仓库 push 成功而后续仓库失败，Worker 必须为已写入仓库生成并推送补偿回滚提交，同时恢复本地知识库和上一活动快照，批次保留为“同步失败、可重试”，不能伪装为已发布。审计记录保存批次 ID、仓库、提交和同步结论，不保存草稿正文。

总览和问题中心不再向单管理员展示处理时限、剩余小时或已超时数量。数据库中的 `sla_due_at` 暂时保留以兼容已有数据，但不参与日常排序和催办；运营优先级只依据严重程度、受影响用户数、重复发生次数、自动复查结论和用户负面反馈。总览改为展示需要人工确认、生成或验证中、验证通过待发布、发布或同步失败以及当前活动版本。

用户反馈继续作为问题发现和修订证据来源，而不是管理员逐条处理的工单。`useful` 只进入质量统计；`incorrect`、`missing` 和 `review_requested` 自动形成或合并问题组；用户反馈与自动复查通过发生冲突时升级为人工确认。反馈永远不能直接训练模型、改写答案或绕过验证发布，原始反馈页降级为记录查询，日常工作统一从问题中心进入。

验收条件：

- 管理员可在第一份草稿生成或验证期间继续处理第二个问题，两个问题的页面状态和自动保存互不覆盖；
- 单机默认同时执行多个复查、生成和验证任务，同一作业不会被重复领取；
- 同一知识库的多个草稿合并为一个提交和一次 push，跨两个知识库显示为一个批次、至多两次 push；
- 同一目标路径的冲突草稿不能进入同一批次；
- 组合回归、Git 基线、upstream 或 push 任一失败时不切换线上版本，部分 push 有补偿回滚记录；
- 批次全部成功后才把草稿标记为已发布、问题标记为已解决并切换活动快照；
- 总览和问题列表不再出现“已经超时”“处理时限”或剩余小时；
- 用户反馈继续参与问题聚类、判断冲突、影响统计和修订证据，但无需管理员逐条推进状态。

## 20. 历史证据重校验与反馈信号

自动复查记录中的正式引用可能来自较早的知识库提交。草稿生成不能仅因为引用的 `revision` 与当前知识库 HEAD 不同就静默丢弃证据；Worker 必须读取当前允许路径并重新计算内容哈希。历史引用的内容哈希与当前文件一致时，视为“版本已前进但证据内容未变化”，允许以当前文件作为正式证据，并记录重新校验数量。内容哈希不同、文件不存在或无法读取时仍必须拒绝该引用，并把可读原因返回管理后台。当前答案卡明确治理的路径以当前知识库文件为准，但当前版本引用若哈希不一致仍按完整性异常阻断。

用户反馈是问题信号而不是事实来源。`incorrect`、`missing`、`review_requested`、`evidence` 和 `correction` 必须作为独立结构化字段传给修订 Agent，并与用户补充、原问题、原回答和自动复查缺陷一起参与根因判断。Agent 提示必须明确：反馈分类和用户文字可以指出需要核查的位置，但不能替代正式知识库证据，也不能单独生成可发布事实。

修订工作台必须展示本次生成实际加载的正式证据数量、历史引用重新校验数量和不可用引用原因。无证据时，主操作改为“重新校验正式证据并生成”；帮助文字说明系统会读取当前知识版本，证据未变化时不会产生新的可用答案，避免把重复执行误解为模型已经修订。页面不要求管理员理解 revision、hash 或原始错误码。

验收条件：

- 历史引用与当前文件内容哈希一致时可被重新校验并进入修订 Agent；
- 历史引用对应文件已变化、缺失或不可读时不进入 Agent，并在后台显示中文原因；
- `/q 2` 以结构化“答案错误”信号进入 Agent，上述信号不能被当作正式证据；
- 草稿详情返回证据数量、历史引用重校验数量和问题列表，旧草稿保持向后兼容；
- 无证据状态不再提示盲目“重新生成完整草稿”，恢复动作和结果可解释；
- 当前失败草稿重新处理后至少加载到已校验正式证据，是否可发布仍由 Agent 输出和既有门禁决定。

## 21. 问法边界与分层验证解释

答案卡 `aliases` 只保存脱离聊天上下文仍能独立表达完整意图的同义问法和口语问法。五类验证问题中的 `follow_up` 只用于验证多轮对话承接，不得因为生成了回归问题就写入答案卡别名；`negative` 继续只作为边界负例。标准问法保存在 `canonical_question`，同义和口语问法保存在 `aliases`，上下文追问与边界负例保存在回归验证记录中。已有答案卡别名和管理员明确保存的独立问法继续保留。

单条修订验证由三个彼此独立的门禁组成：问法命中检查、修订 Agent 的结构与必答项检查、独立回答复查。最终结果必须同时满足适用门禁，不能用其中任意一层的“通过”覆盖另一层失败。管理后台在最终结果旁显示决定该结果的原因：未命中时说明命中检查失败，结构检查失败时显示 Agent 说明，独立复查为 `needs_review` 或 `fail` 时优先显示复查结论。通过行也应概括各层均已通过，不再使用含义不清的“处理失败”或只显示“模型判定通过”。

验收条件：

- `alias` 和 `colloquial` 回归问法可进入答案卡 `aliases`，`follow_up` 和 `negative` 不进入；
- 上下文追问仍保留在五类回归验证中，且不要求直接精确命中答案卡；
- 独立回答复查为 `needs_review` 或 `fail` 时，该用例最终失败并显示复查摘要；
- 问法命中失败、结构检查失败和内容复查失败均有不同的中文原因；
- 验证表使用“已通过/未通过”表达用例结论，状态不只依赖颜色，移动端不新增横向溢出。

## 22. 必答概念的确定性可验证边界

答案卡 `requiredConcepts` 只保存能够在正式证据和标准答案中直接定位的原子事实，例如模块名、动作、配置项或数据口径。`核心功能`、`职责区别`、`协作关系`、`相关内容` 和 `关键信息` 等分类标签不能作为受治理概念，因为它们没有稳定的文字或事实边界，会导致答案已经陈述具体事实却仍被判缺失。

修订 Agent 生成草稿后必须执行确定性自洽预检。发现抽象概念时，系统在同一次生成任务内要求 Agent 用证据中的具体事实重写；旧答案卡中的抽象概念可在重新生成时被具体概念替换，禁答主张、证据路径和其他有效安全边界继续保留。连续两次仍无法形成可验证规则时，草稿保持不可发布并返回明确阻塞原因。

隔离验证在调用独立复核模型之前识别抽象概念，返回 `rule_conflict`，并展示必答项 ID、具体概念、字段、证据路径和“修改规则”动作。普通回答复查不再把抽象标签当作必须逐字出现的答案内容；语义完整性仍由必答项复查结论判断。验证详情必须显示真正缺失的概念，不能只显示“缺少受治理概念”或把整段答案作为唯一原文。

验收条件：

- `deliveragent 核心功能` 被识别为不可确定验证的抽象规则，而不是答案缺项；
- `病毒扫描`、`反垃圾检查`、`投递至 mssvr` 等具体事实继续接受确定性覆盖检查；
- 修订 Agent 第一次产生抽象概念时能够在一次受控纠错后生成原子概念；
- 未修改的旧抽象规则重新验证时返回稳定的规则冲突，不调用独立复核模型；
- 后台显示具体规则和修改动作，现有证据、安全、发布与回滚门禁不回归。
