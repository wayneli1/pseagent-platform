# PSEAgent 答案卡目录、连续追问与 PostgreSQL 持久化设计

日期：2026-08-05  
状态：已确认，开始实施  
对应基线：`2026-08-05-live-answer-review-feedback-ux-design.md`

## 1. 当前问题

1. 线上问答使用两套 Git 知识库编译出的答案卡目录，但运营后台“答案卡”页只读取 `card_revisions`。目录与运营表没有同步，所以线上已有卡片时后台仍显示空白。
2. 用户反馈已经关联 request id、原问题、原回答、论客聊天名和答案卡命中摘要，但页面没有清楚展示“自动复查 → 用户反馈 → 人工修订”的关系，运营人员难以理解反馈的用途。
3. 连续追问上下文只保留最近用户问题，不保留上一轮回答结构。“那密码呢”通常可解析，“把刚才第二点展开”无法可靠解析。
4. 当前本地集成进程使用内存 Store，进程重启后答案卡修订、反馈、复查和作业会丢失。

## 2. 总体决策

- 运营主库采用 PostgreSQL。Supabase 是带鉴权、对象存储和托管能力的 PostgreSQL 平台；当前内网、含加密运营数据的场景不需要额外平台依赖，优先使用企业可控 PostgreSQL。
- 两套 Obsidian/Git 知识库仍然是知识正文和已批准答案卡的事实来源；PostgreSQL 保存运营镜像、人工修订、反馈、复查、作业、发布和审计，不取代 Git。
- 已发布目录通过 Worker 幂等同步到 `card_revisions`，来源标为 `catalog-sync`。相同卡片、相同内容和相同 Git revision 不重复建修订；任何实际变化生成下一修订。
- 用户反馈不会自动改写知识库，也不会自动成为“正确答案”。它是人工运营信号，必须与同一 request id 的自动复查联合查看，最后由运营人员创建或修改答案卡并通过审核、回归和发布。
- 连续追问只携带受限的“问题 + 回答提纲”，不携带无限全文。提纲去除资料来源段，限制行数、单行长度和总长度，既支持“第二点”引用，又控制提示注入和上下文膨胀。

## 3. 答案卡同步闭环

```text
两套 Git 知识库
  -> 编译并校验答案卡目录
  -> Worker 幂等同步 card_revisions
  -> 后台显示“知识库目录”来源
  -> 运营人员查看 / 新建草稿 / 审核
  -> 回归门禁
  -> 发布与 Git 回写
```

Worker 启动时自动排队一次目录编译；后台同时提供“同步知识库答案卡”按钮。同步失败以作业失败呈现，不清空既有卡片。后台空状态必须说明数据来源并提供同步动作。

## 4. 反馈与复查闭环

```text
每条已交付回答 -> 自动复查（系统判断）
用户发送 /q  -> 用户反馈（体验信号）
request id    -> 关联两条记录
运营详情页     -> 同时查看反馈、原问原答、自动复查
人工判断       -> 修订答案卡或知识正文
审核 + 回归    -> 发布后才影响后续回答
```

`/q 1` 可用于监测满意度和发现自动复查误报；`/q 2`、`/q 3`、`/q 4` 提高人工处理优先级。任何反馈内容都只作为候选线索，不能绕过审核直接成为线上答案。

## 5. 连续追问上下文

序列化契约升级为 version 3：

```json
{
  "version": 3,
  "recentTurns": [
    { "question": "……", "answerOutline": "1. ……\n2. ……" }
  ]
}
```

仅成功交付的 `answered` 或 `partially_answered` 轮次进入上下文。`/new` 清空当前用户上下文；不同用户严格隔离；重复发送同一问题时不附带自身历史；总字符数超过上限时优先保留最新完整轮次，最后才截断最新问题和提纲。

## 6. 数据与密钥边界

- PostgreSQL 保存加密后的聊天名、问题、回答和用户补充；数据库、日志、审计元数据不出现这些明文。
- AES-256-GCM 密钥和访问令牌哈希仅放在未纳入 Git 的 `.env.local` 或生产密钥管理系统。
- 本地使用独立数据库 `pseagent_ops_live`，不覆盖现有测试数据库和无法解密的历史记录。
- 启动顺序为迁移数据库、启动 Ops API、启动 Worker、启动 Bridge。API 与 Worker 共享同一 PostgreSQL 和同一密钥环。

## 7. 验收条件

- 后台答案卡页可看到当前两套知识库的全部已批准目录卡，重复同步不产生重复修订。
- 页面明确区分“知识库目录”和“运营修订”，空状态带原因和同步动作。
- 用户反馈详情能打开同 request id 的自动复查；页面说明反馈不会直接训练或污染知识库。
- 连续追问“那密码呢”和“把刚才第二点展开”均能从上一轮受控上下文解析；`/new` 后不再继承。
- 使用 PostgreSQL 运行完整问答、反馈和复查流程后，重启 API 与 Worker，数据数量和内容仍可读取。
- 单元测试、类型检查、构建、数据库迁移、端到端接口和后台视觉检查通过。
