# PSEAgent 逐回答自动复查与低负担反馈设计

日期：2026-08-05
状态：已确认，开始实施
对应基线：`2026-08-05-answer-card-knowledge-ops-platform-design.md`

## 1. 问题结论

当前系统没有真正独立的逐回答自动复查。在线 `verifier` 属于回答生成链路，依赖同一份 TaskSpec；TaskSpec 漏掉必答项时，生成和校验会一起漏判。用户不发送 `/q` 时，Knowledge Ops 不会保存问题和回答，也不会产生复查工单。发布回归只验证固定用例，不能替代真实回答复查。

现有反馈交互还存在两个负担：`/q 4` 要求用户编写正确答案，不符合企业用户的时间投入；“可补充说明”没有给出可照抄的示例。后台只显示伪匿名 ID，是因为论客聊天名未进入标准消息契约，反馈数据也没有加密保存该字段。

## 2. 目标

1. 每一条成功交付的专业库或通用库回答自动进入独立复查，不依赖用户反馈。
2. 复查使用固定模型 `deepseek_v4_flash`，但使用独立提示词、独立任务和重新读取的正式知识证据，不采信在线 verifier 的“完整”结论。
3. 已批准精确答案卡的必答项成为独立复查的权威检查表，避免 TaskSpec 漏项被共同放过。
4. 用户只需选择体验结果；`/q 4` 改为请求人工复查，不再要求用户提供正确答案。
5. 反馈工作台显示论客聊天名；聊天名与问题、回答一样加密存储，不进入明文数据库、日志或审计元数据。
6. 运营人员可以纠正误点的反馈分类，所有修改留审计记录。
7. 自动复查故障不得阻塞或撤回已经交付的回答，但必须在后台形成可见的待处理异常。

## 3. 两条独立闭环

```text
回答生成链路
  -> 在线 verifier（交付前，防止无证据输出）
  -> 回答交付
  -> 自动提交 AnswerReviewCase
  -> 独立 Worker 重新加载已批准答案卡与引用页面
  -> deepseek_v4_flash 独立判定
  -> pass / needs_review / fail
  -> “反馈与复查”工作台

用户体验链路
  -> /q 1 有帮助
  -> /q 2 有错误（原因可选）
  -> /q 3 没讲全（缺失内容可选）
  -> /q 4 我不确定，请人工复查
  -> FeedbackCase
  -> “反馈与复查”工作台
```

两条记录使用 `requestId` 关联，但不混用分类。自动复查表达系统判断，用户反馈表达用户体验；用户选“有帮助”不能把自动复查的失败结论覆盖为通过。

## 4. 用户反馈交互

回答后的菜单固定为：

```text
—
这次回答怎么样？回复一条命令就可以：

/q 1  有帮助
/q 2  有错误
/q 3  没讲全
/q 4  我不确定，请人工复查

愿意补充时，直接写在命令后面，例如：
/q 3 没提到客户端专用密码
```

选项 2、3、4 的说明均为可选。选项 4 映射为 `review_requested`，用于提高人工复查优先级，不要求用户掌握或撰写正确答案。原有专家命令 `/feedback #编号 evidence <说明>` 保留；历史 `correction` 数据继续可读，但不再作为普通用户快捷选项。

反馈成功后明确说明已记录；选项 4 的确认文案说明系统会核对正式知识依据，且不要求用户补写答案。格式错误提示同时给出四个有效命令和一条补充示例。

## 5. 身份与隐私

`LunkrDirectMessage` 从消息发送人结构中提取可见聊天名，并进行 NFKC、空白折叠、长度限制和控制字符清理。`peerUid` 仍只用于会话键和 HMAC 伪匿名关联。

`userDisplayName` 进入反馈和自动复查的 AES-256-GCM 加密载荷，不创建明文列，不写日志，不写审计 metadata。只有具备 `feedback:read` 或 `answer_review:read` 权限的后台请求会在服务端按页解密并返回聊天名。旧记录或论客事件未携带名字时显示“未获取到聊天名”，不得用 UID 冒充名字。

相较此前“仅主动反馈才持久化正文”的边界，本阶段按用户明确授权，将每条成功交付的知识域回答加密保留用于自动质量复查。普通运行日志仍不保存问题、回答、聊天名、知识正文或路径。保留周期、导出和删除策略由部署配置控制，生产默认应采用最短可运营周期。

## 6. 自动复查契约

`AnswerReviewCase` 分开记录：

- 处理状态：`queued`、`running`、`completed`、`errored`；
- 机器结论：`pending`、`pass`、`needs_review`、`fail`；
- 人工状态：`open`、`in_review`、`resolved`、`dismissed`；
- 缺陷分类：`knowledge_gap`、`retrieval_gap`、`planning_gap`、`coverage_gap`、`logic_gap`、`citation_gap`、`expression_gap`；
- 严重度：`critical`、`major`、`minor`。

提交载荷包含 request id、伪匿名用户 id、加密聊天名、问题、最终回答、回答状态、知识范围、正式引用标识、答案卡匹配摘要和交付时间。引用只接受双知识库当前 revision 下的相对 Markdown 路径和内容哈希。

Worker 复查时重新编译已批准答案卡目录，重新读取并校验引用文件，构造独立证据包。模型只能依据该证据包判定，不得使用外部知识补足。模型输出必须通过严格 JSON Schema；缺引用、引用漂移、模型不可用或输出无效都不能静默通过，而是标记 `errored` 或 `needs_review` 并保留人工入口。

能够从运行摘要唯一定位已批准答案卡时，模型必须逐项返回 obligation 覆盖结论；任何 required obligation 缺失，整体不得为 `pass`。引用支持与回答主张冲突时为 `fail`；证据不足但无法证明错误时为 `needs_review`。复查输入和界面文案必须使用运行时真实的 `exact/family/partial` 匹配类型，不得把通过卡片哈希定位到问题族卡片误写成“精确命中”。

## 7. 工作台信息架构

侧栏名称改为“反馈与复查”。页面顶部展示四项：待处理用户反馈、待人工复查、自动通过、复查执行异常。主体使用两个带清晰标题的区块：

1. “自动复查”：默认只看待人工项，可筛机器结论、处理状态和人工状态；列表显示聊天名、问题摘要、结论、分数、缺陷数、时间。
2. “用户反馈”：显示聊天名、反馈类型、处理状态、回答状态和时间；详情中可修改反馈分类与处理状态。

聊天名为普通文本列，不再标为“匿名”。伪匿名 ID 仅在详情的技术信息中按需展示。复杂信息通过抽屉逐层展开，操作使用可见标签、持久帮助文字、明确成功/失败状态和键盘焦点；列表不依赖颜色单独表达状态。

自动复查详情展示：问题、回答、结论摘要、逐 obligation 结论、缺陷、引用校验结果、模型名和人工处理状态。系统不得自动向用户发送“纠错答案”；只有人工批准后的知识修订和回归发布才能影响后续回答。

## 8. 在线门禁补强

自动复查是发现漏网问题的第二道网，不替代交付前门禁：

- 配置声明应启用答案卡但目录缺失、为空或 revision 不一致时，启动必须失败；
- 精确答案卡命中时，使用卡片 obligations 直接编译 TaskSpec，不依赖模型先猜出必答项；
- `answerCardActivation` 必须随回答元数据进入复查记录，匹配但未激活自动进入待人工；
- 激活失败属于答案卡治理链路告警，文案必须显示真实匹配类型和脱敏 Guard issue code，不得表述为回答事实已经出错；
- 已批准精确卡片的 required obligation 未达到 complete 时，不得把回答标为完整。

## 9. 验收

- 无需发送 `/q`，每条成功知识回答均产生且只产生一条自动复查记录；
- 同一 request id 重试提交幂等；
- 第一题“腾讯企业邮箱迁移前置设置”能命中已批准卡片，O1、O2 均被检查，漏掉微信绑定、安全登录、客户端专用密码或 IMAP/SMTP 时不得判为通过；
- `/q 4` 无备注也能提交人工复查；`/q 3 没提到客户端专用密码` 能保存备注；
- 工作台显示论客聊天名，数据库明文搜索不到聊天名；
- 管理员修改误点分类后可见新分类，并有不含正文和姓名的审计记录；
- 自动复查模型名只能是 `deepseek_v4_flash`；
- Knowledge Ops 或 Worker 不可用时，回答仍可交付，失败在脱敏运行事件中可观测；
- 服务、Worker、Bridge、管理后台的单测、类型检查、构建和本地端到端流程通过。
