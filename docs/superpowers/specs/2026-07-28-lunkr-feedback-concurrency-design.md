# Lunkr 问题回执、四用户并发与会话重置设计

日期：2026-07-28

分支：`feature/lunkr-direct-integration`

状态：已确认设计，尚未实施

## 1. 背景与问题证据

真实 Lunkr 问答记录显示，现有直连链路已经能够完成普通问题、Coremail 专业知识问题、通用售前知识问题、连续追问和引用回发，但存在以下体验与正确性问题：

1. 知识问题通常需要约 1–2 分钟，处理期间没有任何回执。
2. 同一用户连续发送两题时，后续答案无法直观看出对应哪一道题。
3. 同一用户虽然已经串行执行，但现有队列不暴露等待状态、队列位置或开始执行状态。
4. 当前不同用户没有全局并发上限，可能同时占用过多模型和 Knowledge Engine 资源。
5. 长答案按字符边界拆分，出现列表项从中间断开、缩进损坏、来源列表无分段标识等问题。
6. `/new` 在真实记录中被当作普通问题送入模型；后续追问仍使用原 CACTER 上下文，证明会话没有清空。
7. 失败提示没有问题编号，也没有内容无关的停止原因记录，难以事后区分模型波动、规划失败、最终校验失败或超时。

`/new` 的现象可以确认是集成 bug，但现有日志没有保存原始消息正文，尚不能断言根因一定是零宽字符、全角字符或富文本包装。实施必须先用真实 Lunkr 消息形态建立失败测试，再修复规范化边界。

## 2. 目标

- 每个普通文字问题到达后立即返回带编号的确认消息。
- 同一用户严格串行，明确展示该用户前方等待问题数量。
- 不同用户最多同时执行 4 个问题，并保证用户之间公平调度。
- 每个用户的问题编号、队列、取消控制和上下文完全隔离。
- 最终回答、失败回答和长答案所有分段都能映射到原问题编号。
- `/new` 立即建立新会话边界，中止该用户旧任务并清空旧上下文。
- 长答案按完整段落、列表和来源块分段，不破坏 Markdown 结构。
- 暂时性模型故障在 300 秒总预算内最多自动重试一次。
- 日志足以定位队列、阶段和停止原因，同时不记录问题、答案、UID 或凭据。

## 3. 非目标

- 不支持群聊、图片、文件或语音问答。
- 不新增 OpenClaw、Lunkr MCP 或远程消息中间件。
- 不把队列、编号或上下文持久化到磁盘或数据库。
- 不实现跨 Windows 进程或多机器的分布式调度。
- 不实现任意问题的 `/cancel <编号>` 命令。
- 不创建 Windows 服务或开机启动项。

## 4. 用户可见消息协议

### 4.1 问题编号

- 每个 Lunkr UID 独立递增，从 `#1` 开始。
- 编号仅在当前进程生命周期内有效，进程重启后重置。
- `/help`、`/new`、空消息和附件不消耗问题编号。
- 重复消息先经过现有去重器；被判定为重复时不得再次发送回执或消耗编号。

### 4.2 立即回执

问题获得执行槽并立即开始时：

```text
已收到问题 #12，正在处理。
```

同一用户已有活动问题或等待问题时：

```text
已收到问题 #13，前面还有 1 个问题，已加入队列。
```

该用户当前没有活动问题，但 4 个不同用户的执行槽均已占用时：

```text
已收到问题 #1，当前服务繁忙，已进入等待队列。
```

等待问题实际取得执行槽时：

```text
问题 #13 已开始处理。
```

不发送周期性“仍在处理”心跳，避免聊天刷屏。

### 4.3 最终回答

单段回答：

```text
问题 #13 的回答：

<回答正文>
```

多段回答：

```text
问题 #13（1/3）

<第一段>
```

后续段分别标记为 `（2/3）`、`（3/3）`。所有段使用同一问题编号。

### 4.4 失败回答

暂时性故障在允许的一次内部重试后仍未恢复：

```text
问题 #13 处理失败：知识问答服务暂时不可用，请稍后重试。
```

失败问题不写入连续对话上下文，也不阻塞同一用户的下一题。

## 5. 调度模型

### 5.1 用户内串行

每个 `peerUid` 同一时刻最多执行一道题。该用户后续问题进入自己的 FIFO 等待队列，并在回执中展示该用户前方的问题数量。

每个用户最多保留 5 道尚未开始的问题。超过上限时不分配问题编号、不进入队列，固定回复：

```text
当前已有较多问题等待处理，请稍后再发送。
```

### 5.2 四用户并发

全局限制表达的是“最多 4 个不同用户同时执行”，而不是不区分用户的 4 条任务：

- 一个用户无论等待多少题，同一时刻都只占一个执行槽。
- 四个不同用户可以各执行一道题。
- 第五个用户进入全局等待集合。
- 某题结束后，所属用户必须释放执行槽；如果该用户还有下一题，它与其他等待用户一起重新竞争，不得连续占住槽位。

### 5.3 公平性

调度器维护可执行用户的 FIFO/轮转队列，而不是把所有问题放入一个容易被单一用户填满的全局问题队列。

一个用户完成当前问题后，如果仍有等待问题，只能被放到可执行用户队列尾部。这样既保持用户内顺序，也使其他用户获得执行机会。

### 5.4 配置

新增本机运行配置：

```text
LUNKR_MAX_ACTIVE_PEERS=4
LUNKR_MAX_PENDING_PER_PEER=5
```

两项必须为正整数；首期默认值分别为 4 和 5。

## 6. 组件边界

运行链路拆为五个职责单一的组件：

```text
Lunkr 私聊事件
  → 消息标准化与命令识别
  → 用户编号与立即回执
  → 四用户并发调度器
  → PSEAgent
  → 答案呈现与 Lunkr 回发
```

### 6.1 消息标准化与命令识别

标准化只负责把 Lunkr 真实文本表示转换成规范纯文本：

- Unicode NFKC 规范化；
- 清理首尾普通空白、BOM 和零宽字符；
- 从已确认的 Lunkr 富文本包装中提取纯文本；
- 不执行 HTML、脚本、Markdown 或任意命令；
- 规范化后只对完整文本精确识别 `/help` 和 `/new`。

必须先捕获或构造与真实失败事件一致的输入形态，使现有实现稳定复现 `/new` 被当作普通问题的错误，再确定最小修复。不得凭猜测一次加入大量宽松匹配。

### 6.2 用户状态

每个用户在内存中维护：

- 下一个问题编号；
- 会话 epoch；
- 当前活动任务及其 `AbortController`；
- 最多 5 个等待问题；
- 最近 6 轮、最多 12,000 字符的现有对话上下文。

UID 仅作为进程内 Map 键，不进入普通日志。

### 6.3 并发调度器

调度器负责：

- 同一用户互斥；
- 最多 4 个活动用户；
- 等待用户公平轮转；
- 返回“立即执行、用户内排队、全局繁忙、用户队列已满”四种入队结果；
- 一个任务失败、超时或取消后可靠释放槽位。

调度器不读取问题正文、不调用模型，也不管理上下文。

### 6.4 PSEAgent 调用

桥接层把每个任务自己的 `AbortSignal` 传给 PSEAgent。PSEAgent 继续负责路由、规划、知识检索、引用验证和 300 秒总请求预算。

暂时性模型错误只在剩余预算允许时重试一次。可重试范围限于网络中断、HTTP 408/429/5xx 和模型服务临时不可用；认证错误、配置错误和稳定的契约错误不得盲目重试。现有无效 JSON/schema 修复仍按其独立的一次修复规则执行。

### 6.5 答案呈现

呈现器只处理：

- 问题编号前缀；
- 回答分段；
- 分段总数与序号；
- Markdown 段落和列表完整性；
- 引用组合与资料来源按数字升序展示。

呈现器不改变事实、覆盖状态、引用归属或知识库选择。

## 7. `/new` 会话边界

`/new` 是高优先级控制命令，不作为普通问题进入 PSEAgent，也不消耗问题编号。

收到有效 `/new` 后按以下原子顺序处理：

1. 增加该用户的会话 epoch。
2. 中止该用户当前活动问题。
3. 丢弃该用户尚未开始的等待问题。
4. 清空该用户连续对话上下文。
5. 发送固定确认：

```text
已开始新会话，之前处理中和排队的问题已取消。
```

6. `/new` 之后到达的问题属于新 epoch，使用空上下文。

旧 epoch 的异步任务即使晚到完成结果，也不得回发答案、写入新上下文或发送额外失败提示。其他用户的任务、队列和上下文不受影响。问题编号继续递增，不因 `/new` 重置。

`/help` 直接返回帮助文本，不取消任务、不清空上下文。

## 8. 长答案分段

现有 1,000 字符上限继续保留，但分段算法必须为编号前缀预留字符，并按以下优先级选择边界：

1. 完整的“资料来源”块；
2. Markdown 列表项或连续列表块；
3. 空行分隔的段落；
4. 完整句子；
5. 只有单个不可拆超长块时才使用硬字符边界。

算法先计算正文段，再加入 `问题 #N（i/总数）` 前缀；若加入前缀后超限，必须重新分段。不得发送空段，也不得改变正文字符顺序。

连续引用如 `[2][1]` 可在呈现层稳定规范为 `[1][2]`；资料来源列表按引用编号升序排列，但不得重新编号或引入未使用来源。

## 9. 故障与取消

- 回执发送失败：不得启动对应模型任务；按现有三次短重试后记录脱敏发送错误。
- 回答发送失败：不得重复生成答案；只重试发送。
- PSEAgent 暂时不可用：受 300 秒总预算约束重试一次，仍失败则发送带编号失败提示。
- 问题超时：发送带编号失败提示，释放执行槽，继续下一题。
- `/new` 取消：旧任务不发送失败提示，避免在“新会话已开始”之后出现旧消息。
- Lunkr Socket 重连：进程内活动任务不重复入队；消息 ID 去重继续生效。
- 进程退出：内存队列、编号和上下文自然丢失；首期不恢复未完成问题。

## 10. 可观测性与隐私

运行日志允许记录：

- 每进程加盐哈希后的用户标识；
- 用户本地问题编号；
- `received`、`queued`、`started`、`answered`、`failed`、`cancelled`；
- 用户内等待数量和全局活动用户数量；
- PSEAgent 的 `scope`、`status`、停止原因、耗时和引用数；
- Lunkr 发送是否成功。

运行日志禁止记录：

- 原始 Lunkr UID；
- 问题和答案正文；
- 知识页正文；
- 密码、验证码、SID、Cookie、Session 和模型密钥。

诊断日志保持系统临时目录限制，并继续按显式开关启用。

## 11. 自动化测试

### 11.1 调度

- 5 个不同用户同时提问：前 4 个执行，第 5 个等待。
- 同一用户连续发送 3 题：只执行第 1 题，后两题保持 FIFO。
- 一个用户排队不阻止其他用户获取空闲槽位。
- 用户完成一题后回到轮转队尾，不连续垄断槽位。
- 同一用户等待 5 题后，第 6 道等待题被明确拒绝。
- 成功、失败、超时和取消都释放槽位。

### 11.2 回执与编号

- 每道有效文字问题只分配一个编号并立即回执。
- 用户内排队数准确。
- 全局繁忙时使用繁忙回执，不泄露其他用户身份。
- 排队任务开始时只发送一次开始提示。
- 最终回答和全部分段使用相同编号。
- 重复 Lunkr 消息不重复编号、回执或回答。

### 11.3 `/new`

- 干净 `/new`、全角斜杠、零宽字符、首尾空白和已确认的真实富文本包装都能识别。
- `/new` 不调用 PSEAgent。
- `/new` 中止当前任务、删除等待任务并清空上下文。
- 被取消旧任务晚到完成时不能回发或写上下文。
- `/new` 不影响其他用户。
- 回归序列：
  1. 询问 CACTER 核心功能；
  2. 追问“做 POC 时最容易遗漏什么”，确认能使用上下文；
  3. 发送 `/new`；
  4. 再问“刚才说的 POC 是什么产品”，确认不能继续使用旧 CACTER 上下文。

### 11.4 分段与故障

- 长列表不能从列表项中间拆分。
- “资料来源”尽量保持为完整块。
- 每段包含正确的 `i/总数`，且不超过 Lunkr 字符上限。
- 引用与资料来源按数字升序显示。
- 暂时性模型错误最多重试一次，总耗时不超过 300 秒。
- 失败问题不进入上下文，后续问题继续执行。

## 12. 真实 Lunkr 验收

### 场景 A：同一用户连续提问

连续发送：

1. “第一次拜访企业客户时，如何使用 SPIN 方法了解客户需求？”
2. “客户认为方案价格太高，售前应该如何分析异议并推进下一步？”

要求：

- 两题立即获得不同编号；
- 第二题显示用户内等待数量；
- 第二题开始时发送开始提示；
- 失败或最终答案都能明确对应编号；
- 两题总流程中不得出现无编号的通用失败提示。

### 场景 B：不同用户并发

用自动化假 UID 验证 5 用户调度；真实 Lunkr 至少用 2 个用户同时提问，确认：

- 两个用户并行开始；
- 编号和上下文各自独立；
- 一个用户的连续问题不阻塞另一个用户。

### 场景 C：上下文与 `/new`

复用 11.3 的 CACTER/POC 序列，要求命令固定回复、旧任务取消、旧上下文不可见。

### 场景 D：长答案

使用 CACTER 核心能力与 POC 复合问题，要求所有分段都有编号和段号，列表结构完整，资料来源排序稳定。

## 13. 完成标准

- 所有 Lunkr Direct、PSEAgent、Knowledge MCP 和 Knowledge Engine 测试通过。
- 新增调度、命令、分段、重试与隐私测试全部通过。
- TypeScript 类型检查和构建通过。
- 真实 Lunkr 场景 A、C、D 通过，场景 B 至少完成 2 个真实用户并行与 5 个假 UID 自动化验证。
- Knowledge Engine 继续绑定已确认的两个固定 revision。
- Lunkr 与 Knowledge Engine 运行日志不包含正文或凭据。
- OpenClaw 与 Lunkr MCP 仍不进入运行链路。
