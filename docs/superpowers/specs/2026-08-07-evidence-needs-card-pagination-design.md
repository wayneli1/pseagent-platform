# PSEAgent 正式资料待补与答案卡分页设计

日期：2026-08-07
状态：已确认，开始实施
对应基线：`2026-08-05-exception-driven-knowledge-ops-design.md`、`2026-08-05-catalog-continuity-postgres-design.md`

## 1. 问题

修订 Agent 已能在证据不足时生成 `publishable=false` 草稿并阻止发布，但问题组仍停留在 `in_progress`。管理后台因此把已经完成证据判断的项目显示为“修订中”，普通问题队列也持续把它们计入可立即处理事项。管理员看不到一个集中清单来判断应向正式资料库补充什么内容。

答案卡页面当前一次读取并渲染全部 `card_revisions`。卡片与历史修订持续增加后，页面会越来越长，详情操作还会再次读取全量列表。

## 2. 设计结论

新增问题状态 `awaiting_evidence`，中文名称为“待补正式资料”。它表示系统已完成本轮修订判断，但现有正式资料不足以形成可发布答案；该状态不是发布失败、无需处理或已解决。

管理后台新增一级页面“资料待补”。普通问题队列继续承载可直接生成、编辑、验证或发布的事项；资料待补页面集中展示被证据门禁阻止的项目。总览提供数量提醒和直达入口。

答案卡列表采用服务端分页，每页 25 条。列表只读取当前页，详情使用单修订接口读取，不再为打开一张卡加载全部修订。

## 3. 状态与恢复流程

流程调整为：

```text
待处理 -> 修订中 -> 待验证 -> 已解决
              |
              +-> 待补正式资料 -> 重新校验证据并生成 -> 修订中 / 待补正式资料
```

当草稿不可发布且阻断类型为 `evidence_required` 时，Worker 将问题更新为 `awaiting_evidence`。逻辑缺陷、系统修复或人工裁决不能误归为资料缺口。

`awaiting_evidence` 不进入问题中心默认“可立即处理”统计，但仍属于真实未解决问题，可在“全部阶段”筛选中查看。管理员不能把该状态直接推进到已解决；补充正式资料后，从资料待补页面或修订工作台执行“重新校验正式证据并生成”。重新生成排队后暂时进入 `in_progress`；证据仍不足则回到 `awaiting_evidence`，形成可解释闭环。

历史不可发布草稿根据加密提案内容进行兼容分类。只把明确缺少正式资料、证据覆盖或知识页面来源的草稿迁入 `awaiting_evidence`，不根据用户反馈内容直接推断事实。

## 4. 资料补充清单

不可发布提案可携带加密的 `evidenceRequest`：

- `summary`：需要补充的资料主题；
- `requiredMaterials`：建议补充的正式资料类型与核心内容；
- `acceptanceCriteria`：资料入库后能够重新生成答案前必须满足的条件。

该内容属于管理员决策信息，继续随修订提案加密保存，不新增问题组明文正文列，不进入作业载荷、日志或审计元数据。旧草稿没有结构化清单时，服务根据目标知识域、问题类型、标准问题和阻断原因生成保守的兼容清单；兼容清单只描述“需要什么资料”，不生成产品事实或答案。

专业知识问题的默认清单要求正式产品、版本、实施、迁移或运维资料，至少覆盖适用范围、前置条件、操作步骤、验证方法、例外、回退或升级边界。通用售前问题的默认清单要求正式方法、流程或制度资料，至少覆盖角色、决策/预算/资源核验口径、适用与排除条件、审批边界和记录模板。

资料入库验收统一要求：来源可追溯；标明适用产品或业务范围、版本/日期和维护责任；核心结论可在正文直接定位；用户反馈和模型推测不得作为唯一事实来源；边界、例外和验证方式必须明确。

## 5. 资料待补页面

页面是独立一级导航，不使用弹窗承载主流程。首屏展示：

- 待补项目总数及目标知识库分布；
- 每个项目的资料主题、目标资料库、阻断原因、建议资料清单、入库验收标准和最近更新时间；
- 唯一主要操作“打开资料需求”，进入原问题的修订工作台；工作台保留“重新校验正式证据并生成”。

页面使用服务端分页，每页 25 条；空状态说明当前没有被证据门禁阻止的项目。阻断状态使用警告色并同时显示文字，不依赖颜色表达。长内容按项目卡片分组，资料条目使用语义列表；键盘焦点可见，操作点击高度不低于 44px，375px 宽度不得产生页面横向滚动。

问题中心筛选增加“待补正式资料”。该状态的下一步文案为“查看待补资料”，帮助说明为“正式资料不足，等待补充后重新校验证据”，不再显示“后台管理员正在修订”。

## 6. API 与分页契约

新增管理员接口：

- `GET /v1/evidence-needs?limit=25&offset=0`：返回 `{items,total}`，只包含 `awaiting_evidence` 项；
- `GET /v1/revisions/:revisionId`：返回单个答案卡修订详情；
- `GET /v1/cards?limit=25&offset=0`：返回 `{items,total}`，按更新时间倒序。

分页参数最小 1、最大 100，偏移量不得为负。答案卡创建时的修订号计算继续读取同卡历史，不通过分页列表推算，避免并发和截断错误。

## 7. 数据与兼容

PostgreSQL 扩展 `issue_cases.status` 检查约束，加入 `awaiting_evidence`。迁移只更新符合明确阻断条件的现有活动草稿；应用层仍会读取加密提案进行最终兼容归类。

`RepairDraftProposal` 新增可选 `blockingKind` 和 `evidenceRequest`，以兼容既有加密草稿。新生成的证据阻断提案必须写入 `blockingKind=evidence_required` 和结构化资料清单；旧提案通过服务端保守回退展示。

答案卡同步、审批、发布、回滚、双知识库事实来源和 GitHub 同步流程保持不变。

## 8. 验收条件

- 证据不足草稿生成后，问题自动进入“待补正式资料”，不再显示“修订中”；
- 逻辑问题、系统修复和人工裁决不进入资料待补页面；
- 当前四个被证据门禁阻止的问题全部归入资料待补页面，并分别展示资料主题、补充清单和入库标准；
- 普通问题中心默认待办不再包含这四项，“全部阶段”仍可查询；
- 补充资料后可从原草稿重新校验证据，证据仍不足时稳定回到资料待补状态；
- 资料需求正文只通过管理员鉴权接口解密返回，不新增明文数据库列或审计正文；
- 答案卡每页 25 条，上一页/下一页边界、总数和显示区间正确；
- 打开答案卡详情不触发全量列表读取；
- Knowledge Ops、Worker、管理后台测试、类型检查和生产构建通过；管理后台在 375、768、1280 和 1440 宽度无新增横向溢出。
