# Lunkr 会话编号与知识证据覆盖门补充设计

日期：2026-07-28

分支：`feature/lunkr-direct-integration`

状态：用户已确认设计，尚未实施

## 1. 背景与已确认问题

本设计补充两个彼此隔离、但需要一起进入真实验收的正确性问题。

### 1.1 Lunkr 问题编号长期递增

当前问题编号以 Lunkr UID 为单位保存在进程内，从 `#1` 开始递增。`/new` 会增加会话 epoch、取消旧任务并清空上下文，但不会重置下一个问题编号。因此 Windows 服务长期不关闭时，同一用户看到的编号会持续增加。

用户已选择方案 B：

- `/new` 后从 `#1` 开始；
- 连续 24 小时没有成功提交普通文字问题时，下一次普通文字问题静默开始新会话并从 `#1` 开始；
- 自动新会话不向用户发送额外通知。

### 1.2 正文未覆盖但状态为 `answered`

真实问题：

```text
Coremail 是否已经支持 2035 年量子卫星邮件协议
```

运行记录显示该问题被路由到 `professional`，最终记录为：

```text
status=answered
referenceCount=2
```

回答正文同时说明知识库没有“2035 年量子卫星邮件协议”资料，只引用了介绍 SMTP、POP3、IMAP、HTTP/HTTPS 和 Coremail 私有协议的相关页面。该回答没有证明目标命题，却被模型标记为 `coverage=complete`。

当前结构校验只能证明：

- 引用编号存在；
- 页面确实为对应 requirement 读取过；
- 回答中的内联编号与 citations 元数据一致；
- `complete` 或 `partial` 至少有一个引用。

它不能证明“引用正文直接支持用户询问的结论”。状态映射随后直接信任模型给出的 coverage，因此把这类“只找到相关背景、没有目标证据”的回答映射为 `answered`。`AnswerService` 又只在正式结果严格等于 `not_covered` 时调用 Coremail MCP，所以该问题没有触发历史辅助查询。

## 2. 目标

- 同一用户的问题编号具有清晰的会话边界，不因本机服务长期运行而无限累加。
- `/new` 和 24 小时闲置都建立新的隐藏 epoch，并使新会话从 `#1` 开始。
- 旧 epoch 的迟到结果不能进入新会话。
- 正式知识回答只有在实际读取正文支持目标命题时才能标记为 `answered` 或 `partially_answered`。
- “页面主题相关”与“页面正文支持结论”严格区分。
- 正式知识库完全未覆盖时，正式结果保持固定 `not_covered` 和零正式引用。
- 只有经过覆盖校验的完全 `not_covered` 才允许调用 Coremail MCP。
- Coremail MCP 始终作为可能包含较多错误的低可信历史线索展示，不能改变正式状态或污染后续上下文。
- 保持专业库、通用库、普通问题和 Lunkr 通道之间的现有边界。

## 3. 非目标

- 不引入 Embedding、重排序模型或向量数据库。
- 不同时搜索专业库和通用库。
- 不把 PSEAgent 自身说明加入任一知识库。
- 不放宽 Coremail MCP 的触发条件。
- 不使用 Coremail MCP 修正、重写或补齐正式知识答案。
- 不持久化 Lunkr 编号、epoch、队列或上下文。
- 不引入 OpenClaw 或 Lunkr MCP。
- 不修改两个知识库仓库的内容或 revision。

## 4. 方案选择

### 4.1 仅增强提示词

只在现有知识代理提示词中增加“相关页面不等于覆盖”的要求，改动最小且没有额外模型调用，但最终 coverage 仍由同一次生成自行声明，无法形成独立检查。真实问题已经证明提示词约束不足。

不采用。

### 4.2 使用关键词或否定词规则

可以检测“未提及”“无法确认”等词并强制改为 `not_covered`，但会误伤“知识页明确证明不支持某功能”的合法否定回答，也无法覆盖更多隐蔽的证据错配。

只可作为测试辅助，不作为主判定机制。

### 4.3 独立证据覆盖校验门

在知识代理形成结构合法的草稿后，增加一次独立、严格 Schema 的证据覆盖校验。校验输入只包含原问题、规划后的必答项、草稿答案与引用，以及这些引用对应的实际紧凑正文。

校验器负责逐项判断正文是否直接支持目标命题，并输出经审计的最终 requirement 结果。它只能维持或降低草稿 coverage，不能升级。

本设计采用该方案。它不依赖 Embedding，能够复用本次请求已经读取的知识页，并在 5 分钟总等待上限内增加一层针对性检查。

## 5. Lunkr 会话编号

### 5.1 用户状态

每个 `peerUid` 在内存中独立维护：

- `sessionEpoch`：隐藏会话代次；
- `nextQuestionId`：当前会话下一个显示编号；
- `lastAcceptedQuestionAt`：最近一次成功获得编号并进入调度器的普通文字问题时间；
- 当前活动任务和等待队列；
- 当前会话的连续对话上下文。

不同用户的编号、闲置时间和 epoch 互不影响。

### 5.2 手动 `/new`

收到有效 `/new` 后，以该用户为范围执行：

1. `sessionEpoch += 1`；
2. `nextQuestionId = 1`；
3. 清除 `lastAcceptedQuestionAt`；
4. 中止当前活动问题；
5. 丢弃全部等待问题；
6. 清空连续对话上下文；
7. 发送现有固定确认：

```text
已开始新会话，之前处理中和排队的问题已取消。
```

其他用户不受影响。

### 5.3 24 小时闲置自动新会话

新增本机配置：

```text
LUNKR_SESSION_IDLE_MS=86400000
```

默认值为 24 小时，必须为正整数，主要用于自动化测试和后续本机调整。

普通文字问题进入调度器之前检查：

```text
lastAcceptedQuestionAt 已存在
且 now - lastAcceptedQuestionAt >= LUNKR_SESSION_IDLE_MS
```

满足条件时，先执行与 `/new` 相同的 epoch、编号、任务、队列和上下文重置，再把当前问题作为新会话 `#1` 提交。这个自动重置不发送“已开始新会话”提示，只发送当前问题正常的“已收到问题 #1”回执。

以下输入不更新 `lastAcceptedQuestionAt`：

- `/help`；
- `/new`；
- 附件、图片、文件或语音；
- 空白消息；
- 被消息 ID 去重器拒绝的重复事件；
- 因该用户等待队列已满而拒绝的问题。

只有成功分配问题编号并进入活动或等待调度的问题才更新时间。

### 5.4 epoch 与迟到结果

调度任务继续携带提交时的 `sessionEpoch`。回发开始提示、失败提示、答案分段和写入上下文之前，都必须验证任务 epoch 仍是当前值。

手动或自动新会话后，旧 epoch 即使晚到完成，也不得：

- 回发答案；
- 回发失败提示；
- 写入新会话上下文；
- 改变新会话编号；
- 释放或操作不属于自己的新 epoch 任务。

### 5.5 进程重启

编号和上下文仍不持久化。进程重启后所有用户自然从新 epoch 的 `#1` 开始，不发送额外说明。

## 6. 正文证据覆盖校验门

### 6.1 数据流

正式知识问答调整为：

```text
路由
  → 固定单一知识域
  → 必答项规划
  → 搜索和读页
  → 知识代理生成结构化草稿
  → 现有引用结构校验
  → 独立正文证据覆盖校验
  → 再次执行引用结构校验
  → 状态映射与正式回答格式化
  → 仅完全 not_covered 时尝试 Coremail MCP
```

普通问题的 `normal` 路径不进入该校验门。

### 6.2 校验输入

读页时除现有引用元数据外，在本次请求内存中保存：

- requirement ID；
- 引用编号、标题和路径；
- 已提供给知识代理的紧凑正文；
- 草稿 requirement 的 coverage、answer 和 citations；
- 原始问题和规划后的 requirement question。

正文只存在于本次请求内存和模型输入中，不写入普通运行日志。

### 6.3 直接支持规则

逐项判定必须遵守：

- 页面明确给出用户询问的事实、机制、步骤、数值、边界或结论，才能作为支持证据。
- 页面只讨论相邻主题、基础协议、同类产品或宽泛背景，不算覆盖目标命题。
- 页面没有提及某能力，不能据此推导“不支持”。
- 页面明确写明“不支持”“尚未提供”或等价结论时，可以支持否定回答。
- 如果用户询问的是“现有资料是否覆盖或是否明确”，页面明确列出的资料缺口可以成为该问题的直接证据。
- 回答中的每个事实结论必须能映射到保留的引用；无法映射的结论必须删除或标为未覆盖。
- `complete` 表示该 requirement 的核心问题全部得到直接支持。
- `partial` 表示只有可独立使用的一部分得到直接支持，并明确指出剩余缺口。
- `none` 表示没有任何足以回答目标问题的直接证据，citations 必须为空。

“知识库只列出 SMTP、POP3、IMAP 等协议，没有提及 2035 年量子卫星邮件协议”只能说明检索到的页面未覆盖目标命题，不能证明 Coremail 已支持或不支持，因此该单一 requirement 必须为 `none`。

### 6.4 校验输出与单向降级

校验器使用严格 JSON Schema，逐项输出：

- requirement ID；
- 审计后的 `complete|partial|none`；
- 仅包含证据支持内容的最终 answer；
- 仅包含直接支持该项结论的 citations；
- 内容无关的 reason code，供诊断使用。

覆盖等级顺序为：

```text
none < partial < complete
```

审计后的等级不得高于草稿等级；引用必须是草稿引用与该 requirement 已读引用的子集。校验器不能新增引用、读取新页面、重新搜索或改变知识域。

校验输出还要经过现有引用结构校验。最终格式化只能消费审计后的结果，不能继续使用未审计草稿。

### 6.5 状态映射

- 所有 requirement 为 `complete` 且存在有效正式引用：`answered`。
- 至少一项为 `partial` 或 `none`，同时至少一项有直接支持证据：`partially_answered`。
- 所有 requirement 为 `none`，或审计后没有任何有效正式引用：`not_covered`。

完全 `not_covered` 必须使用现有固定正式文本：

```text
当前知识库暂未覆盖该问题，暂时无法给出可靠答案。
```

此时正式 `references=[]`，相关但不支持目标命题的页面不得继续作为正式来源展示。

### 6.6 校验故障

覆盖校验必须服从现有 300 秒请求总预算，并为最终格式化预留时间。

如果校验模型不可用、超时或连续两次输出不符合 Schema：

- 返回 `temporarily_unavailable`；
- 不保留未经校验的 `answered` 草稿；
- 不伪装成 `not_covered`；
- 不调用 Coremail MCP。

这样可以继续保证“只有确认完全未覆盖时才查历史资料”，而不是把技术故障误判为知识缺口。

## 7. Coremail MCP 低可信历史线索

### 7.1 触发条件不变

Coremail MCP 当且仅当审计后的正式知识结果严格等于 `not_covered` 时调用。

`answered`、`partially_answered`、`temporarily_unavailable` 和 `normal` 都不得调用。Coremail MCP 调用失败时仍返回原始正式 `not_covered`，不覆盖为服务不可用。

### 7.2 用户可见展示

正式答案必须先独立展示：

```text
当前知识库暂未覆盖该问题，暂时无法给出可靠答案。
```

存在历史辅助结果时，再展示完全隔离的区块：

```text
⚠️ Coremail MCP 低可信历史线索（可能不正确）

以下内容由 Coremail MCP 根据 Jira/Wiki 历史资料自动整理，并非正式知识库答案，也未经过产品或售前人员验证。内容可能存在较多错误、过时信息、资料缺失或版本不匹配，请仅作为继续检索的线索，不能直接用于客户答复、投标、部署、升级或变更决策。

<Coremail MCP 原始辅助回答>

历史来源：
<Jira/Wiki 来源>
```

该警告作为共享字面量进入数据契约和所有文本呈现测试，不能由调用方省略或替换成弱提示。

Coremail MCP 返回的 `confidence` 不是正式可信度。若继续展示，必须标为：

```text
MCP 自报置信度：<值>（不代表内容正确）
```

无论自报值为低、中或高，都不能减弱固定警告。

### 7.3 隔离规则

历史辅助信息：

- 不得改变正式 `status=not_covered`；
- 不得进入正式 `answer` 或正式 `references`；
- 不得由 PSE 模型总结、修正、扩写或改写；
- 不得作为下一轮 Lunkr 连续对话上下文；
- 不得作为后续问题的知识证据；
- 不得进入专业库或通用库；
- 只能以独立 `historicalAnswer` 数据和独立历史来源展示。

Lunkr 屏幕上可以完整展示历史辅助区块，但 ConversationStore 只能保存正式知识回答的安全上下文，不保存该低可信区块。

## 8. 可观测性与隐私

### 8.1 Lunkr 运行日志

现有脱敏日志增加：

- 隐藏 `sessionEpoch`；
- `resetReason=manual|idle`；
- 当前会话本地 `questionId`。

同一用户在不同 epoch 中都可能出现 `#1`，诊断时使用加盐 peer 哈希、epoch 和 question ID 组合定位。日志仍不得记录 UID、问题正文、回答正文或凭据。

### 8.2 PSEAgent 诊断日志

覆盖诊断增加：

- 草稿 coverage；
- 审计后 coverage；
- 保留的引用编号；
- 内容无关的 reason code；
- 校验成功、Schema 修复、超时或不可用停止原因。

诊断日志不写知识页正文、问题正文、答案正文或 Coremail MCP 内容。

## 9. 自动化测试

### 9.1 编号与闲置会话

- 新用户第一题为 `#1`。
- 同一会话连续问题按 `#1`、`#2` 递增。
- `/new` 后下一题为 `#1`。
- `/new` 取消活动和等待任务并清空上下文。
- 距最近成功提交问题恰好小于 24 小时时不重置。
- 距最近成功提交问题恰好等于或超过 24 小时时静默重置，下一题为 `#1`。
- `/help`、附件、空消息、重复消息和队列满拒绝不延长闲置时间。
- 一个用户自动重置不影响其他用户。
- 旧 epoch 迟到的开始提示、失败和答案都被抑制。
- 进程重建后编号从 `#1` 开始。

时间测试使用注入时钟，不真实等待 24 小时。

### 9.2 正文覆盖校验

- 页面明确支持目标命题：保持 `complete/answered`。
- 页面明确否定目标命题：允许证据化的否定 `complete/answered`。
- 页面仅包含相邻背景但没有目标结论：降为 `none/not_covered`，正式引用为空。
- 页面完全未提及目标能力：不能推导“不支持”。
- 部分必答项有直接证据、其余没有：`partially_answered`，只保留支持项引用。
- 校验器不能升级草稿 coverage，不能新增引用。
- 校验器返回未知引用或不合法 Schema：修复一次，仍失败则 `temporarily_unavailable`。
- 校验器不可用时不调用 Coremail MCP。
- 审计后全部为 `none` 时，Coremail MCP 最多调用一次。
- 审计后仍为 `answered` 或 `partially_answered` 时不调用 Coremail MCP。

加入固定回归问题：

```text
Coremail 是否已经支持 2035 年量子卫星邮件协议
```

在当前固定知识快照中预期：

- `scope=professional`；
- 正式 `status=not_covered`；
- 正式 `references=[]`；
- 配置 Coremail MCP 时允许附加低可信历史辅助区块；
- 无论历史辅助区块内容为何，正式状态不改变。

### 9.3 历史辅助展示与上下文

- 标题必须包含“低可信”和“可能不正确”。
- 固定警告必须完整出现并位于历史正文之前。
- MCP 自报置信度必须带“不代表内容正确”。
- 历史来源与正式来源完全分离。
- `structuredContent.status` 仍为 `not_covered`。
- 下一轮发给 PSEAgent 的 conversation context 不包含历史辅助回答、警告和历史来源。

## 10. 真实 Lunkr 验收

服务只在用户明确允许后启动。自动化验证通过后执行：

1. 连续提问两题，确认编号递增和队列行为不变。
2. 发送 `/new`，确认下一题从 `#1` 开始且旧上下文不可见。
3. 用测试配置缩短闲置阈值，确认自动新会话无额外通知且下一题为 `#1`；随后恢复 24 小时默认值。
4. 询问“Coremail 是否已经支持 2035 年量子卫星邮件协议”。
5. 检查脱敏诊断，确认专业知识库正文覆盖校验得到 `none`，正式结果为 `not_covered`。
6. Coremail MCP 可用时，确认屏幕先显示正式未覆盖，再显示醒目的低可信警告、原始历史内容和历史来源。
7. 继续追问，确认发给 PSEAgent 的上下文不包含低可信历史内容。

## 11. 完成标准

- Lunkr Direct、PSEAgent、Knowledge MCP 和 Knowledge Engine 的现有测试全部通过。
- 新增编号、闲置会话、epoch、正文覆盖校验、历史警告和上下文隔离测试全部通过。
- TypeScript 类型检查和构建通过。
- 固定“2035 年量子卫星邮件协议”回归通过。
- 正式知识覆盖状态只由审计后结果产生。
- Coremail MCP 仍只在正式完全 `not_covered` 时触发。
- 历史辅助内容始终明确标记为可能不正确，且不污染正式答案、正式引用或后续上下文。
- 两个知识库保持只读和单域检索。
- OpenClaw 与 Lunkr MCP 不进入运行链路。
