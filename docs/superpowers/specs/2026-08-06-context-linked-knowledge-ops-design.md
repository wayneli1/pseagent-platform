# PSEAgent 上下文关联知识运营设计

日期：2026-08-06  
状态：已确认，开始实施  
对应基线：`2026-08-05-exception-driven-knowledge-ops-design.md`

## 1. 当前缺口

Lunkr 在线回答已经能用最近问题和回答提纲解析“第二点怎么操作”等追问，但自动复查与知识运营只保存当前原始问题、回答、引用和答案卡摘要。后台看不到父问题、系统解析后的完整问题或会话关系；复查与修订 Agent 因而可能把依赖上下文的追问误当成独立问题。

## 2. 总体决策

- PostgreSQL 持久化 Lunkr 会话和已成功回答的轮次，服务重启后仍可承接未过期会话。
- `/new` 立即结束当前会话；默认 24 小时无新问题自动结束。不同伪匿名用户严格隔离。
- 每轮同时保存用户原始问题、系统解析后的完整问题、是否使用上下文、继承主体、父请求、回答提纲和答案卡关联。
- 只有解析器明确返回 `contextUsed=true` 时建立父子关系。仅时间相邻但主题独立的问题保留在同一会话中，不绑定父问题。
- 自动复查、问题聚类和修订 Agent 以解析后的完整问题作为业务判断问题，同时保留原始问题用于审计和后台展示。
- 上下文追问不得进入答案卡 `aliases`。修订应落在其关联答案卡或解析后的独立意图上。

## 3. 明文存储边界

按用户本阶段明确决定，新增的会话和轮次关联字段暂不加密，使用 PostgreSQL 明文列保存：会话 ID、伪匿名用户 ID、原始问题、解析后问题、上下文使用标记、继承主体、回答提纲、父请求 ID、答案卡匹配摘要和时间。

现有反馈、完整回答、聊天名、用户补充和修订草稿继续沿用原加密载荷，不因本次决定改为明文。普通日志和审计元数据仍不得写入问题、回答提纲或聊天名正文。后续可以通过独立迁移把上下文字段切换为加密载荷。

## 4. 数据模型

新增 `conversation_sessions`：

- `session_id`：UUID；
- `pseudonymous_user_id`：伪匿名用户标识；
- `source`：固定为 `lunkr_direct`；
- `started_at`、`last_activity_at`、`expires_at`；
- `ended_at`、`end_reason`：`manual`、`idle` 或空。

新增 `conversation_turns`：

- `turn_id`、`session_id`、会话内稳定递增的 `turn_index`、`request_id`、展示用 `question_id`；
- `parent_turn_id`、`parent_request_id`；
- `raw_question`、`resolved_question`、`context_used`；
- `inherited_subjects`、`answer_outline`；
- `answer_status`、`scope`、`answer_card_match`；
- `answered_at`、`created_at`。

`request_id` 全局唯一，`session_id + turn_index` 唯一。`question_id` 允许在 Bridge 重启后重新编号，不承担数据库唯一性。活动会话按伪匿名用户查询并在事务中续期。过期会话先标记为 `idle`，再创建新会话。

## 5. 在线链路

```text
收到问题
  -> 从 Knowledge Ops 读取该用户活动会话最近 6 轮
  -> 组装 version=3 的问题 + 回答提纲上下文
  -> 问题解析器生成 resolvedQuestion/contextUsed/inheritedSubjects
  -> 检索、回答并交付
  -> 成功后持久化轮次并返回 session/parent 关系
  -> 自动复查与反馈关联同一 request id
```

Knowledge Ops 暂时不可用时，回答仍可使用进程内的受限上下文继续工作；持久化失败不得撤回答案，但该轮后台明确缺少上下文关系。恢复后不猜测或伪造缺失父子关系。

## 6. 复查、聚类与修订

- 自动复查优先使用 `resolved_question`，并同时收到 `raw_question`、父问题和回答提纲，避免脱离语境判定。
- 有答案卡关联时，追问缺陷继续聚合到相同答案卡与缺陷类别；没有答案卡时，使用解析后问题而不是“第二点怎么操作”的原文计算问题指纹。
- 修订 Agent 的记录包含 `question`（解析后完整问题）、`rawQuestion`、`contextUsed` 和父问题摘要。
- 追问揭示某个必答项遗漏时修订现有答案卡；只有解析后的问题确实形成独立、可复用意图时才允许创建新卡。

## 7. 管理后台

自动复查、反馈详情和修订工作台增加“对话上下文”区：

```text
腾讯企业邮箱迁移到 Coremail 前需要哪些设置？
└─ 第二点怎么操作？                     上下文追问
   系统理解：客户端专用密码应该如何生成和配置？
```

界面原则：

- 原始追问与系统理解并列，不能用系统改写覆盖用户原话；
- 明确显示“上下文追问”或“独立问题”，不依赖颜色表达；
- 父问题可点击查看关联自动复查；旧记录显示“历史记录，无上下文信息”；
- 技术 ID 默认折叠，不挤占运营主流程；
- 375、768、1024、1440 宽度无横向溢出，焦点和按钮状态可见。

## 8. 验收条件

- 第一问和“第二点怎么操作”形成同一会话，第二问保存解析后的完整问题并绑定第一问 request id；
- 第二问改问明确新主题时 `contextUsed=false`，不建立父子关系；
- API、Worker 或 Bridge 重启后，24 小时内的活动会话仍能恢复最近 6 轮上下文；
- `/new` 后旧上下文不再被读取，数据库会话标记为人工结束；
- 自动复查使用解析后问题，后台展示父子链和系统理解；
- 问题聚类与修订 Agent 不把裸追问建立为独立答案卡或别名；
- 旧记录保持可读并显示无上下文信息；
- PostgreSQL 迁移、专项测试、全仓测试、类型检查、构建和浏览器验收通过。
