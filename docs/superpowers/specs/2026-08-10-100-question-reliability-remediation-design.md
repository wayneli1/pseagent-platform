# PSEAgent 百题可靠性整改设计

日期：2026-08-10

状态：待书面审阅

实施分支：`fix/100题可靠性整改`

## 1. 背景与结论边界

本轮测试原计划执行 100 次真实 `pse_answer`：10 道既有稳定性题各重复 3 次，共 30 次；另补 70 道未使用过的新问法。实际得到 96 条可解析结果，原因是既有题中的 P02、P10 在严重长尾时被停止，少了 4 条记录。因此这批数据是“百题计划下的 96 条观测基线”，不能伪称为完整 100 题，也不能直接称为事实准确率。

当前可确认的基线如下：

| 数据集 | 记录数 | 完整回答 | 部分回答 | 暂时不可用 | 不在范围 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 70 道新问法 | 70 | 20 | 24 | 25 | 1 |
| 既有 10 题重复测试 | 26 | 13 | 12 | 1 | 0 |
| 合计 | 96 | 33 | 36 | 26 | 1 |

合计可返回最终答案 70/96，即 72.9%；完整回答 33/96，即 34.4%。这些数字反映链路可用性和系统自报覆盖度，不代表经过人工金标准核验的事实准确率。

70 道新问法还具有十个主题乘七种提问视角的模板相关性，已在本轮分析中暴露，后续只能进入开发/校准集，不能再作为最终盲测集。

## 2. 已验证的问题证据

### 2.1 可用性和长尾是第一阻断项

70 道新问法中 25 道在外部 180 秒预算附近中止；完整回答的 P50 约 95.6 秒、P90 约 162.6 秒，部分回答的 P50 约 121.8 秒、P90 约 156.3 秒。既有题中还观测到 325.6 秒和 528.4 秒的极端长尾。

现有实现存在叠加等待：

- 请求默认总预算 300 秒，活动预算 270 秒，与本轮 180 秒外部验收预算不一致；
- 模型传输层最多尝试 4 次，并带 1、3、10 秒退避；
- 每进程模型并发固定为 3，但等待队列没有独立排队预算，多进程测试又会绕开这一上限；
- 路由、任务分析、答案卡匹配、知识代理、合成和验证器均可能调用模型；
- 知识代理最多允许 40 个动作回合，并可能进入多种生成修复回合；
- 验证器最多执行 3 次逐段校验和 2 次整体回退；
- 单知识域失败在剩余 30 秒以上时可能整域重跑一次。

这些机制分别看都有容错价值，但没有共享剩余预算和统一重试所有权，组合后形成重试放大、排队长尾和外层先超时。

### 2.2 检索命中与问题义务不一致

P04“Coremail 邮件迁移项目通常需要考虑哪些产品能力”连续 3 次均为部分回答。详细诊断显示实际读取了 O365 迁移前置、运营商级迁移案例和报价资料，却没有稳定命中更贴近“迁移产品能力/组织数据结构/迁移对比”的资料。

这证明至少存在一类“正式资料可能存在，但候选生成、排序或读取预算没有把它送到答案链路”的检索缺陷。此类问题不能直接登记为知识缺口。

### 2.3 覆盖验证器会双向改变结论

70 道新问法的 45 条最终回答中，验证器改变了 16 条覆盖结论：

- 20 条部分回答在草稿阶段已经存在缺口；
- 4 条草稿完整但被验证器降级；
- 4 条草稿存在缺口但被验证器升级；
- 已知 N05、N19、N30、N69 被降级，N10、N22、N25、N29 被升级。

因此验证器既不是纯确定性证据检查，也不是只做安全收缩。它当前承担了语义重判职责，而回答模型与复查模型默认又可能使用同一模型，导致相关性误判和随机波动。

### 2.4 通用 POC 治理问题被过度路由到专业域

70 道新问法中有 5 条路由不匹配，集中在 N64、N65、N66、N67、N69，均属于产品中性的 POC、合同或验收治理问题，预期为 `general`，实际为 `professional`。

现有规则先检查“知识记录”“技术能力”“验证/承诺”等专业域模式，再检查通用售前方法。POC、验收和承诺类表达因此容易被专业域规则抢占。

### 2.5 当前不能先补知识或堆答案卡

已有证据表明，部分失败来自可用性、检索排序、验证器重判和路由，而不都是资料不存在。如果现在直接补资料或增加答案卡，会把系统缺陷掩盖成单题规则，增加冲突并污染后续验收。

## 3. 设计目标

本次整改目标不是让已见题变绿，而是建立一条在未见问题、重复调用和受控并发下仍可量化的可靠回答链路。

最终发布门槛：

| 指标 | 门槛 |
| --- | ---: |
| 回答链路成功率 | ≥ 99.5% |
| 单题 P95 延迟 | ≤ 120 秒 |
| 单题 P99 延迟 | ≤ 180 秒 |
| 知识域路由准确率 | ≥ 98% |
| 可回答问题事实准确率 | ≥ 95% |
| 高风险事实准确率 | ≥ 99% |
| 无证据关键主张 | 0 |
| 引用支持率 | ≥ 98% |
| 同题三次结论一致率 | ≥ 95% |
| 新版本相对冻结基线退化 | 不超过 2 个百分点 |
| 错误发布或越权承诺 | 0 |

事实准确率、完整率、证据支持率、合理拒答率和稳定率必须分别报告，禁止合并成一个“通过率”。
回答链路成功率以 100 题三次独立调用的 300 次结果计算；首次 100 次仍单独报告，避免用重复调用稀释首次泛化失败。

## 4. 方案选择

### 方案 A：继续加长总超时

优点是改动小，能减少外层提前中止。缺点是没有消除串行模型调用、重试放大和无界排队，只会把不可用变成长时间等待，也无法改善检索、验证和路由。拒绝采用。

### 方案 B：围绕失败题继续增加关键词、答案卡和资料

优点是已见题改善快。缺点是会污染验收集，把系统缺陷伪装成知识缺口，并扩大规则冲突。拒绝作为主路径；答案卡只保留给高价值、高风险、边界明确的问题族。

### 方案 C：可靠性控制面优先，再逐层校准

按“可用性 → 检索 → 验证器 → 路由 → 真实资料缺口 → 独立验收”顺序推进。每层有独立测试、诊断字段、发布门槛和回滚点。采用此方案。

## 5. 总体架构

```text
请求入口
  └─ RequestBudget（总预算、活动预算、剩余预算）
      ├─ AdmissionControl（有界排队、并发配额、过载快速失败）
      ├─ Resolver / Router（确定性优先，模型回退）
      ├─ TaskSpec / DomainPlan（义务与领域冻结）
      ├─ RetrievalCoordinator（按义务/方面检索与排序）
      ├─ Synthesizer（仅使用证据账本）
      ├─ CoverageGate（确定性检查优先）
      └─ SemanticVerifier（仅处理仍有歧义或高风险的片段）
```

全链路共享一个不可增长的剩余预算。任何阶段都不能自行把局部超时当成新的完整预算。传输重试与业务重试必须只有一个所有者，且只对明确的瞬时故障执行。

## 6. 分阶段设计

### 阶段 148：冻结设计、基线和仓库边界

本阶段只提交设计，不改变运行逻辑。

仓库边界：

- `pseagent-platform`：调用链、模型调度、检索编排、验证器、路由、测试运行器和报告；
- `coremail-professional`：经证据审计确认缺失的产品/技术正式知识；
- `presales-general`：经证据审计确认缺失的通用售前方法知识；
- `coremail-knowledge-mcp`：历史 Jira/Wiki 只读连接器，本轮不写回历史系统；
- `pseagent-platform-status-progress`：只是平台仓库的另一个 worktree，不属于本轮分支，不改动。

### 阶段 149：可执行实施计划

将本设计拆成逐文件、逐测试的 TDD 计划。每个实现阶段都遵循：先写失败测试并观察失败，再写最小实现，运行局部测试，最后运行仓库级验证。

### 阶段 150：链路可用性和模型编排

新增统一请求预算和阶段预算：

- 每次模型调用记录角色、操作、排队时长、执行时长、尝试次数、结束原因和剩余预算；
- 模型槽位等待设置独立上限，队列有最大长度，超限返回可诊断的过载结果；
- 传输层只对 408、425、429、5xx 等明确瞬时故障重试，并受剩余预算约束；
- 禁止路由修复、验证修复、整域重试与传输重试无上限相乘；
- 整域重试只允许在“尚未产生可用证据、故障可重试、剩余预算足够”时发生；
- 低风险且确定性检查通过的答案不再因可选复查不可用而整体失败；高风险答案仍失败关闭；
- 为并发 1、2、4、10 分别输出吞吐、排队、P50/P95/P99 和失败原因。

本阶段不通过简单增大 300/270 秒默认值来达标。180 秒是外部硬上限，内部应留出格式化和返回余量。

阶段门槛：受控并发 1、2、4 下不得出现无界排队；故障必须能归因到排队、传输、规划、检索、合成或验证；历史回归不得出现证据安全退化。

### 阶段 151：按义务检索和来源排序

检索单位从“整题一个宽查询”收紧为“义务 × 证据方面”：

- 每个义务拥有独立候选预算、读取预算和停止条件；
- 排序显式使用标题/主题匹配、方面覆盖、正式来源级别、直接性和新鲜度；
- 报价、案例和历史线索不再因词面重合挤掉更直接的产品能力或方法资料；
- 历史资料只能作补充线索，不得替代正式知识；
- 诊断报告保留候选来源、得分分解、淘汰原因和实际读取路径；
- 明确区分 `source_absent`、`candidate_not_recalled`、`candidate_not_ranked`、`candidate_not_read` 和 `evidence_insufficient`。

P04 迁移能力问题作为开发回归，必须证明直接资料进入候选并被读取，而不是只让最终状态变为 `answered`。

阶段门槛：冻结检索金标准集召回率 ≥ 95%；直接来源不得再被低相关报价/案例稳定挤出；引用安全规则全部通过。

### 阶段 152：覆盖验证器约束和校准

验证链路拆为两层：

1. 确定性层检查引用存在、引用已读、片段引用归属、义务 ID、客户输入状态和显式禁用主张；
2. 语义层只判断确定性层无法判定的“证据是否支持该片段”。

验证器约束：

- 义务集合、义务顺序、证据 ID 和待验证片段在进入验证器后不可修改；
- 验证器不能新增事实、删除义务、重新规划或把客户待补输入误判为知识缺口；
- 从 `partial` 升级为 `complete` 必须有确定性完整性证据；
- 从 `complete` 降级必须指出具体片段和具体不支持原因；
- 复查模型不可用时，低风险且确定性检查通过的内容保留原安全结论，高风险内容失败关闭；
- 用已标注的升级、降级和不变样本分别计算混淆矩阵，不以总通过率掩盖误判。

阶段门槛：校准集中的无依据升级为 0；无具体片段理由的降级为 0；同输入重复三次的覆盖结论一致率 ≥ 95%。

### 阶段 153：通用 POC、合同和验收路由

调整规则优先级和语义边界：

- 产品中性的 POC 组织、合同边界、验收流程、角色职责、风险沟通和升级机制默认进入 `general`；
- 明确包含产品、版本、模块、协议、接口或技术能力核验时进入 `professional`；
- 同时要求产品事实和售前方法时，由 TaskSpec 拆成多域义务，不能用单一关键词抢占整题；
- 低置信度路由交给模型，但模型输出必须受显式信号和会话主题边界校验；
- 新主题不得被旧会话域无条件继承。

阶段门槛：冻结路由集准确率 ≥ 98%；N64/N65/N66/N67/N69 对应的问题族全部覆盖，且专业技术 POC 反例不得退化。

### 阶段 154：真实资料缺口和高风险答案卡

先对剩余失败逐条做证据审计：

```text
正式资料存在且可回答？
  ├─ 是，但没召回/没排序/没读取 → 返回阶段 151 修系统
  ├─ 是，已读取但答案遗漏 → 修生成或验证，不补资料
  └─ 否 → 登记 source_absent，进入对应知识仓库
```

只有 `source_absent` 才允许修改知识仓库。知识提交必须说明来源、适用版本、边界和不能承诺的事项，不重新上传或解析专业 PDF，只使用仓库已提交的 Markdown 索引和正式材料。

答案卡只用于高风险、高价值、边界稳定的问题族；必须有适用域、版本/修订绑定、义务契约、证据绑定、失效条件和回滚方式。禁止为普通长尾问法逐题建卡。

各知识仓库独立验证、独立中文提交、独立推送，绝不跨仓库暂存。

### 阶段 155：历史回归与全新盲测

最终验收分四层：

1. 所有历史回归题，证明没有退化；
2. 当前 70 道新问法作为已见校准集，只证明已知缺陷没有回归；
3. 100 道全新冻结盲测题，题面不得与仓库题库、答案卡标准问法或本轮 70 题重复；
4. 并发 1、2、4、10 的负载剖面，区分单用户质量和过载行为。

100 道盲测按专业知识、通用售前、综合多域、多轮追问、证据不足和安全边界分层抽样。每题独立调用 3 次，共 300 次；首次输出计算泛化指标，三次全部用于稳定性指标，不选最好答案。

盲测矩阵在实施期间保持封存，只保存哈希和分层数量；代码冻结后才首次运行。首次运行后即使失败也不边测边改，原始结果、模型名、知识修订、代码提交、时间和评分全部固化。

若最终未达到门槛，结论必须是“未达到企业级验收”，并按错误类型给出下一轮开发集，不能继续修改同一盲测集后重算通过率。

## 7. 诊断和数据契约

每个请求至少记录以下非敏感字段：

- requestId、代码提交、模型角色与模型名、知识库修订；
- 阶段开始/结束时间、排队时长、执行时长、剩余预算；
- 每层尝试次数、错误码、是否可重试、是否发生降级；
- 路由信号、最终域、TaskSpec 义务 ID；
- 每义务候选数、读取数、来源等级、淘汰原因；
- 草稿覆盖、确定性验证结果、语义验证结果和最终覆盖；
- 引用数量、引用路径哈希和证据支持评分。

不得把 API 密钥、完整会话原文、客户敏感数据或模型原始推理写入诊断文件。测试报告默认写入系统临时目录；需要提交的报告必须先脱敏。

## 8. 提交、推送和回滚

每一阶段：

1. 只在对应仓库工作；
2. 先运行本阶段局部测试，再运行仓库级验证；
3. 检查 `git diff` 和 `git status`，只暂存本阶段文件；
4. 使用中文标题和中文正文提交，正文包含“完成内容”和“验证结果”；
5. 推送当前整改分支或对应知识仓库分支；
6. 报告阶段号、完整提交哈希、验证命令和结果。

每阶段都是独立回滚点。若线上探针出现安全退化，优先关闭新特性开关或回滚当前阶段提交，不回滚无关仓库。

## 9. 非目标

- 不以本轮 96 条结果宣称企业级事实准确率；
- 不把 70 道已见问法继续当盲测；
- 不通过无限延长超时换取表面成功率；
- 不把所有问题答案卡化；
- 不向 Jira/Wiki 历史系统写回；
- 不修改 `pseagent-platform` 主工作区中用户已有的未提交文件；
- 不修改 `pseagent-platform-status-progress` worktree。

## 10. 完成定义

只有同时满足以下条件，才可宣布本轮目标完成：

- 阶段 150—154 的代码和必要知识修订均通过各自测试并已推送；
- 历史回归无超过 2 个百分点的退化；
- 全新 100 题首次盲测和三次稳定性测试均有不可篡改原始报告；
- 第 3 节的最终门槛全部满足；
- 报告明确区分事实准确、完整、证据支持、合理拒答、稳定和可用性；
- 任一门槛未满足时，诚实给出“未达到企业级验收”的结论和可复现缺陷清单。
