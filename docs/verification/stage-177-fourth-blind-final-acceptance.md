## 根因诊断

### P0：新控制面的结构化接口合同不一致

这是本轮首要根因，不能简单归咎于大模型随机。

- 300 次诊断中，`synthesizer/synthesize` 失败 113 次，全部为
  `invalid_schema`。
- `claim_draft` 阶段 101 次 degraded。
- `ModelStructuredClaimSynthesizer`、主张 verifier、目标修订和高风险共识要求模型
  输出 JSON 根数组。
- `OpenAiCompatibleModelClient.completeJson` 明确只接受 JSON 根对象，并在解析后拒绝
  数组；同时默认向网关声明 `response_format=json_object`。

因此真正进入新可靠流水线的主张生成，与通用模型客户端在根结构上先天不兼容。
这属于代码合同缺陷。部分请求仍能回答，是因为 TaskSpec guard 拒绝后回落到了旧链路，
并不证明新控制面成功生成了主张。

### P1：可靠控制面激活覆盖不足

有 TaskSpec 诊断的 250 次请求中：101 次 activated、141 次 guard_rejected、8 次
analysis_unavailable。大量请求仍回落旧 agent 路径，导致新设计的调用上限、义务归并、
主张证据绑定和高风险共识没有统一覆盖所有可回答问题。

### P2：混合域义务和路由未形成稳定并集

混合域首答路由率为 0，证据支持率仅 26.67%。当一个域的 claim draft 失败或 TaskSpec
guard 拒绝时，最终 `domainsUsed`、引用和义务完成状态不能稳定保留双域并集。

### P3：证据不足与安全拒答合同仍未完全对齐评分语义

安全策略本身稳定且危险主张为 0，但部分固定拒答没有覆盖题目要求的具体保护对象、
替代动作或升级概念；证据不足题又受到 claim draft 失败影响，所以合理拒答率只有
36.67%。这不是放宽评分器的理由，应改进确定性拒答/缺口结果内容。

### P4：模型不稳定确实存在，但需在修复 P0 后重新量化

三轮 `invalid_schema` 数分别为 37、39、37；另有 resolver unexpected 8 次、planner
aborted 2 次。同题跨轮状态变化明显，说明模型输出和调用链确实不稳定。但当前最大的
失败源由根数组/根对象合同冲突人为制造；在修复该缺陷前，不能把 35% 不可用率全部
归因于模型本身。

## 下一整改顺序

1. 把所有结构化根数组改为有版本的根对象信封，例如
   `{ "claims": [...] }`、`{ "decisions": [...] }`、`{ "revisions": [...] }`、
   `{ "verdicts": [...] }`；模型客户端继续只接收根对象。
2. 增加真实 OpenAI-compatible 响应夹具，证明 synthesizer、verifier、目标修订和高风险
   共识都能通过同一对象合同；禁止只用绕过模型客户端的 mock 测试。
3. TaskSpec guard 拒绝时不再静默回到无限旧 agent 循环。增加确定性最小义务降级，
   或安全失败关闭；所有正式可回答请求必须受模型调用预算和结果归并控制。
4. claim draft 不合约时，先按域形成确定性的 unavailable/not_covered 义务结果，不允许
   丢失另一个已成功域；随后只允许一次“结构修复”调用，不能开放式重答或无限重试。
5. 固化混合域的 expected domain union，验证任一单域失败时仍能准确报告另一域结果与
   缺口，而不是把双域问题误路由为单域。
6. 用固定策略合同补全保护对象、安全替代和升级路径；不修改本套冻结题或评分标签。
7. 修复后先跑结构合同、故障注入、历史回归和负载门禁，再冻结第五套从未运行过的
   100 题做三轮冷验收。本套第四题集只能作为开发诊断集，不再作为未见终验集。
